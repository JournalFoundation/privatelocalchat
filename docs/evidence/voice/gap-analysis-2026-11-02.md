## 2. Plan claims not supported by the evidence

1. **"Lane 1: 895 pass"**: `npm test` at 5e7953e gives 893 pass, 3 skipped, 896 total. Off by two; the figure may include e2e, unstated.
2. **"Storage back to baseline" (Lane 2 and 3, Acceptance)**: contradicted by the plan's own evidence files (row 48). Only OPFS bytes return to baseline in tests.
3. **"iPhone 15 Pro ... on dev and on production: ios-system-voice-only, no offer, no voice engine, probe, storage check, worker or runtime file requested"** (Lane 4): there is no evidence file of this run (commit 8eab0a6 is prose only). For the iPhone 11 Pro the only evidence line states a voice-related module (`voice-upgrade.mjs`) was requested. No production-origin phone evidence exists.
4. **"The probe limit (800 ms) and the speed limits were calibrated"**: contradicted by `voice-pick.mjs:16-20` and TECHNICAL-DEBT 42 (the speed limits are placeholders). The 800 ms limit is bracketed between 216 ms (a working N100) and 1,997-4,000 ms (the one failing phone): any value in a 10x gap would have fit.
5. **"Centroid and Boiler ... Kokoro (2.0 to 2.3 times real time ...)" versus the spike "Even a fast desktop CPU cannot stay ahead of playback" (0.56x to 0.86x on the same 16-core Centroid)**: a 2.5-4x difference on the same hardware and model is not explained anywhere (different engine, thread count, sentence, warm-up?). The spike text remains in the plan as written, so the plan contradicts itself, and `qualityProbeMaxMs` 160 was set from the larger numbers while its code comment (`voice-pick.mjs:20`) still cites the 0.56x finding and "unused until an engine exists".
6. **"Nothing from this plan is outstanding" / "Open items: None"**: debt items 41, 48, 49, 51, 52 and the memory-headroom requirement are open; item 41 is stale and false.
7. **"The Galaxy S8+ ... free space moved 288 to 290 MB, so the earlier drop was not caused by the test files"**: no evidence file contains that measurement (no 3.9 MB / 288-290 MB values in docs/evidence). The only recorded numbers show the origin's usage rising 41.9 to 57.8 MB.
8. **"Lane 0 ... seven browser runs across five devices"** versus "six browsers across five devices" versus eight entries in inventory.json: inconsistent.
9. **"Kokoro ... 8 voices"** / `qualityMinMemoryGB`: the 1.2 GB (Kokoro) and 0.5 GB (Kitten) resident estimates in `loadPolicy` have no measurement; debt 48 says about 100 MB. No memory measurement of either engine exists in the evidence.
10. **"Both blockers ... fixed"** (independent review): no review record. Plausible, unverifiable.
11. **Stale correction notices in the plan**: "these factors ... must be re-measured with the corrected pipeline" (Kitten table) is followed by later lane results that did re-measure (S8+ 0.2567 in `lane-results.json`) but the plan never says so; "Unverified: That the Kitten int8 and Kokoro q8 files run under ONNX Runtime Web" is still listed under Unverified though spikes proved it. The plan retains contradictory statements.
12. **Lane 5 "work through the real command path for both voices"**: no stored command output; the harness is scratch (`work/voice-lane.js`).

Claims I found supported: production has no debug code (curl), CDN objects are immutable and CORS-readable, Kitten/Kokoro hashes match `ops/cloudflare/voice-models.json` and the manifests, the Galaxy S8+ numbers quoted (0.26x, 4000 ms) match the evidence, the Kokoro GPU spike numbers match `kokoro-webgpu-spike.json`.

## 4. Plan principles versus reality

### 4a. The iPhone/iPad rule

Plan text: "Safari hides the device model, and the investigation in docs/IPHONE-INVESTIGATION.md shows a hard process memory limit (about 2 GB) that the 2B chat model already nearly fills ... Revisit only after a real-phone test and a separate decision." And "Hard evidence ... The only one today is the iPhone and iPad memory limit."

What the evidence is: IPHONE-INVESTIGATION.md is a single-device investigation of an iPhone 15 Pro (status "open") where the **chat model** (Qwen 2B, with WebGPU/Wasm compiler memory) was killed at the WebContent per-process limit of 2,097,155 KB (`docs/evidence/iphone-single-copy-load-limit.json`, `iphone-current-build-reload-limit.json`). It says explicitly that Linux RSS figures are not iOS footprint and that the cause is unproven in places.

Gaps:
- It is evidence about one phone model, one browser engine, one workload (the chat model loaded). No evidence about any iPad (M-series iPads allow far larger per-process memory), iPhone 16/17 or any phone with 8 GB, or about a 27-97 MB model with a 13 MB runtime on a device with no chat model loaded (for example a user on a connected API, or one who never loaded the local model). The rule blocks all of them.
- The plan ties the rule to "beside the chat model", but the code blocks iOS unconditionally, even when no chat model is resident. The "Memory next to the chat model" mechanism that would have allowed a measured decision was never built (row 14).
- The plan committed to a dev-only spike on the iPhone 15 Pro ("Exploration, not shipping") to gather exactly the evidence needed for a future decision. It was not done (row 65), so the shipped rule has no voice-specific measurement.
- The iPhone 11 Pro (no WebGPU, 4 GB) was never shown to exceed any limit; the "iPhone" evidence is the 15 Pro.
- iPad desktop-mode detection (`Macintosh` + `maxTouchPoints > 1`) is reasonable and tested, but a real iPad was never inventoried (the fleet has none) and no iPad evidence file exists.
The rule is a safe, conservative default (it fails safe, principle 1), so the risk is lost value not harm, but it is mis-described as supported by "hard evidence for all iPhones and iPads".

### 4d. Storage safety and remove/cleanup paths

- Remove path itself is sound: `remove()` unloads, recursively removes the OPFS directory, purges worker/ORT cache entries (`voice-engine.mjs:242-247`); `decline()`, `giveUp()` and the stale-file cleanup in `evaluate()` call it.
- `remove()` swallows errors (`voice-upgrade.mjs:152`): if `removeEntry` throws (locked handle, another tab), the controller still sets `engine: null`, `declinedAt` and reports the system voice, leaving up to 96 MB on disk with no record pointing at it. `evaluate()` will retry cleanup only if a later evaluation runs (it does when `!record.engine`, but the offer is suppressed by `declinedAt` for 30 days so `evaluate()` returns before the cleanup line 195).
- Residue after remove (row 48) is unexplained in the evidence.
- The pre-offer write test writes up to 160 MB of random data on every evaluation (desktop included) once per session on devices that pass stage 1; on flash storage and near-full disks this is wasteful and, on the S8+ class, risky (row 59). It runs before the cheap probe, so a phone that will be rejected on speed has already been loaded with a 160 MB write.
- Two tabs: `removeStale()` in one tab deletes another tab's in-flight `plc-storage-check-*` file (false negative, safe) and cleanup in another tab can delete a partial install (debt 49).
- Desktop Chrome's quota is also a share of the total disk, yet desktop does not require `writeOk` in `pickVoiceEngine` (only the controller's unconditional call does). The pure function therefore has a weaker contract than documented and a second caller (such as the dev action, which uses the controller, or a future one) could skip the check.

## 5. Defects and risks

- **D1 (high): a permanent "fallback" lock-out.** `voice-upgrade.mjs:180-185` `giveUp()` writes `record.fallback`; `evaluate()` line 191 returns `fallback-remembered` forever; nothing clears it (grep: no writer other than `giveUp`/`engineFailed`; no expiry like `GATE_COOLDOWN_MS`). It is triggered by ANY exception in `accept()`: a dropped Wi-Fi during the 96 MB download (retry exhausted, line 116-118), a CDN blip, a 404, a storage quota error. Scenario: user taps "Try it" in a lift, download fails, Settings says "A downloaded voice was tried and removed", and the offer never returns on that device. Related: `decline()` sets `chosen:"os"` (line 136) which is permanent (debt 51) and Settings has no way back; the Remove confirm text promises "You can download it again later" which only the 30-day `declinedAt` path (not the decline path) honours.
- **D2 (medium): Remove while speaking permanently disables the offer.** `remove()` (line 150-156) clears `record.engine`, `engine.remove()` terminates the worker, the pending `speak` rejects, `speech.mjs:73` calls `engine.fail`, `engineFailed()` runs with `record.engine === null`, writes `record.fallback = {engine:null,runtime:true,...}` (line 173) and sets state `fallback`. The offer is blocked by `fallback-remembered` thereafter and Settings shows "tried and removed: runtime: ...". Not tested.
- **D3 (medium): Kokoro and Kitten memory is unmeasured and unmanaged.** The worker reads the 92 MB model into a JS array and passes it to ORT (`worker-kokoro.src.mjs:29,41,46`) holding at least two copies at load; threads `min(4,cores)`; `loadWhen` is never consulted (debt 48), so the model loads at the first read-aloud while the chat model may be resident. On a 4-8 GB Android or a low-memory desktop that has a loaded 2B chat model, this can OOM the tab and the chat with it; the plan's mitigation (principle: fail safe) is not implemented.
- **D4 (medium): No underrun detection and a lax watchdog.** `speech.mjs:54` waits 90 s for a first chunk and 75 s between chunks, so a device slower than the sample suggested (CPU contention from a chat generation in another tab, thermal throttling, battery saver) either stutters indefinitely or sits silent for up to ~90 s. The stage-3 sample is measured once, cold, on an idle machine and never re-measured, while the voice runs beside a generating chat model on the same cores.
- **D5 (medium): Kokoro offer boundary is on measurement noise.** `qualityProbeMaxMs: 160` versus Boiler 150 ms and Centroid 136.8 ms. Probe jitter (the S8+ read 1,997 and 4,000 ms) can flip the same machine between Kokoro (96 MB) and Kitten (27 MB) between sessions; each flip is only recorded as `record.gate` for failures. A user who got Kitten active never gets Kokoro (row 5).
- **D6 (medium): Mobile detection by user agent misses Android "Desktop site"** (UA becomes `Linux x86_64` with touch). `isMobile()` is false so `pickVoiceEngine` skips the mobile `writeOk` requirement and the memory-known requirement (`voice-pick.mjs:72,78`). The controller still always runs the write test (line 203), so the shipped path is safe, but the pure function contract is weaker than its documentation and tests (tests pass UA strings).
- **D7 (low-medium): Settings shows voice copy to ineligible devices and has no opt-in.** `shell.mjs:356-358`. Violates "no extra UI" and provides no way to try the voice after "Not now" (30 days) or "Use the system voice" (forever).
- **D8 (low): `giveUp` after `engineFailed` race.** `engineFailed` calls `void giveUp(...)` without awaiting (`voice-upgrade.mjs:176`); a concurrent `remove()` or the next `speak` can start a fresh worker before the directory is removed, then `route()` returns null (state `fallback`) but `hearSample()` in Settings still uses `record.engine` (null) fine; low impact.
- **D9 (low): Install interrupted by a page close leaves a half-written directory** until the next `evaluate()` with no record; but if `record.engine` is set (a Keep happened earlier and a re-install happens) cleanup is skipped. `install()` calls `removeDirectory()` first (line 130) so a retry is safe.
- **D10 (low): `speak()` queue never rejects pending when `terminate()` is called while a load is mid-flight** is covered by `discardWorker`; no defect found, noted as reviewed.
- **D11 (low): Settings "Hear a sample" does not guard against the Settings page being used while reply read-aloud uses the same engine**: `engine.speak` queue serialises (line 276) so a sample waits behind a long reply with no UI feedback.
- **D12 (low): `privacy/index.html:121`** documents `plc.speechInputUnusable`, a key the HEAD commit stopped writing.
- **D13 (low): Mac Safari lane value `storageAfter` 74,366.8 MB vs 4,102.5 MB and doubled quota** suggests the estimate is not reliable on Safari, yet the stage-1 gate uses `quota - usage` on desktop Safari (only the controller's write test, 160 MB, backs it).
- **D14 (process): the committed evidence cannot be regenerated.** The harness is `work/voice-lane.js` (git-ignored), and e2e voice tests need `VOICE_FILES_DIR`/`VOICE_KOKORO_DIR` and skip silently in CI.

### Verdict

The shipped system delivers the core of the plan: an opt-in, measured, hash-verified, on-device voice (Kitten and Kokoro) with the iOS exclusion, a pure and well-tested decision function, CDN hosting with immutable objects, a Settings card with Remove, a GPL relicence and a production build free of diagnostics, and its engineering (golden-tested text pipeline, honest recording of the S8+ failing) is careful. It does not fulfil the plan's letter in several places that matter: the "memory beside the chat model" requirement was not built, the storage-after-Remove acceptance criterion is contradicted by the project's own device data, the iPhone 15 Pro and production-device checks and the Lane 5/6 outputs have no evidence files, the thresholds other than the probe limit are still guesses (with a razor-thin Kokoro margin and no mid-range phone ever measured), Settings has no opt-in or storage total, a single failed install can disable the feature on a device permanently, and the GPL text and notices are not published with the app. The plan's own "complete, nothing outstanding, thresholds calibrated, storage back to baseline" statements are overstated; the plan and TECHNICAL-DEBT.md disagree with each other.
